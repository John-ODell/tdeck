# Build a keyboard-first Meshtastic T-Deck firmware

A from-scratch T-Deck Plus firmware can be fully Meshtastic-interoperable on US LongFast by getting a small set of things exactly right. On the radio side that means **906.875 MHz, 250 kHz, SF11, CR 4/5, a 16-symbol preamble, sync word 0x2B, explicit header and CRC on**. On top of that sits a **16-byte little-endian header**, **AES-CTR with a nonce built from (packet id, sender)**, a **one-byte XOR channel hash (0x08 for default LongFast)**, nanopb-encoded `Data` protobufs, managed-flooding relay with (from, id) dedupe, routing ACKs, and **X25519 + AES-256-CCM PKI direct messages**. PKI is not optional: since firmware 2.7, nodes reject channel-encrypted text DMs addressed to them. The hardware has no surprises once you know the trap. **GPIO10 must go HIGH before anything else**, because it powers the keyboard, backlight, SD, trackball and audio. The SX1262 needs DIO2 as RF switch and a 1.8 V TCXO on DIO3. The ST7789 needs color inversion, and its backlight is a pulse-counted AW9364. The GPS can be one of two different modules, so it has to be auto-detected. The opportunity is real. The official Meshtastic UI (MUI) is touch-first, locks out the phone app, loses keyboard shortcuts, and has open stability and wake bugs. MeshCore Ultra is polished but is not Meshtastic-compatible and is partly paywalled. No existing firmware combines Meshtastic compatibility with a keyboard-first UI, a phone link alongside the on-device UI, calibrated battery reporting and MUI-compatible offline maps. That combination is the gap.

## Seven radio numbers decide whether anyone hears you

Meshtastic nodes decode only packets whose preset, frequency and sync word all match. A single wrong parameter produces silence, not errors. In `modemPresetToParams()`, LongFast is the `default:` branch: `bwKHz = 250.0f; cr = 5; sf = 11` ([MeshRadio.h](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/MeshRadio.h)). In RadioLib's encoding, `cr = 5` means 4/5. The sync word is `const uint8_t syncWord = 0x2b;`. Pass it to RadioLib as-is and let the library expand it into the SX126x register pair ([RadioLibInterface.h](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/RadioLibInterface.h)). The preamble is **16 symbols** in every release from 2.5 through develop ([RadioInterface.h](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/RadioInterface.h)), not RadioLib's default of 8. Packets use an explicit header with CRC enabled. LDRO is set by `(1 << sf) / bw >= 16`. That works out to 8.19 ms for SF11 at 250 kHz, so LDRO is off ([RadioLibInterface.h](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/RadioLibInterface.h)).

The frequency comes from a hash of the channel name. The US region is defined as 902.0 to 928.0 MHz, 100% duty cycle, 30 dBm power limit, zero spacing and zero padding ([RadioInterface.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/RadioInterface.cpp)), which yields 104 slots of 250 kHz. The slot is `djb2(name) % numSlots`, where djb2 starts at 5381 and computes `hash*33 + c` for each byte. The center frequency is `freqStart + bw/2000 + slot × bw/1000`. Versions 2.5 to 2.7 used `floor()` to count slots ([v2.7.26 RadioInterface.cpp](https://github.com/meshtastic/firmware/blob/v2.7.26.54e0d8d/src/mesh/RadioInterface.cpp)). Version 2.8 uses `round((end − start + spacing) / slotWidth)` and adds padding. For the US both forms give the same answer. One subtlety matters: the default primary channel name is the empty string, and `getName()` substitutes the preset's display name, the literal `"LongFast"` ([Channels.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Channels.cpp)). Hashing "LongFast" gives djb2 = 130429955, and 130429955 % 104 = 19 (0-based). That is the UI's "slot 20", at **906.875 MHz**, which matches the official docs ([meshtastic.org radio settings](https://meshtastic.org/docs/overview/radio-settings/)). A non-zero `channel_num` (1-based) or `override_frequency` overrides the hash.

| Parameter | US LongFast value | Common mistake |
|---|---|---|
| Frequency | 906.875 MHz (slot index 19) | Hashing "" instead of "LongFast" |
| Bandwidth / SF / CR | 250 kHz / 11 / 5 (4/5) | Passing CR as 1 or 4/5 notation |
| Preamble | 16 symbols | RadioLib default of 8 |
| Sync word | 0x2B (RadioLib form) | Writing 0x24B4 by hand, or 0x12 (pre-1.2 firmware) |
| Header / CRC | Explicit / on | Implicit header, CRC off (LilyGO demo default) |
| TX power | min(configured, 30 dBm region cap); SX1262 tops out at 22 dBm | Exceeding the region limit |
| TCXO (T-Deck) | 1.8 V on DIO3, DIO2 as RF switch | RadioLib default of 1.6 V |

Combined with the board settings below, the whole bring-up becomes one RadioLib call: `radio.begin(906.875, 250.0, 11, 5, 0x2B, 22, 16, 1.8, false)`, followed by `setDio2AsRfSwitch(true)` and `setCurrentLimit(140)`. Transmit power is capped at the region's `powerLimit` whenever the configured value is 0 or above the limit ([RadioInterface.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/RadioInterface.cpp)).

## Sixteen header bytes and a counter-mode cipher carry every packet

Every Meshtastic LoRa frame is a fixed 16-byte header followed by an encrypted payload of at most 239 bytes (255 − 16). The struct is `{ uint32 to, from; uint32 id; uint8 flags; uint8 channel; uint8 next_hop; uint8 relay_node; }`, and its source comment says it "has to exactly match the wire layout" ([RadioInterface.h](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/RadioInterface.h)). Every field is little-endian. The `flags` byte packs `hop_limit` (bits 0–2), `want_ack` (0x08), `via_mqtt` (0x10) and `hop_start` (bits 5–7). Senders set `hop_start = hop_limit` on origination ([Router.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Router.cpp)). Receivers treat `hop_start == 0` as a pre-2.3 legacy packet whose `next_hop` and `relay_node` are invalid, and they drop anything with `from == 0` ([RadioLibInterface.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/RadioLibInterface.cpp)). `relay_node` and `next_hop` carry only the last byte of a node number. The originator writes its own byte, and each relayer overwrites it with its own ([NextHopRouter.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/NextHopRouter.cpp)). Broadcast is `0xFFFFFFFF`. As an example, a broadcast from `!12345678` with id 0xABCD, 3 hops, on LongFast serializes as `ff ff ff ff 78 56 34 12 cd ab 00 00 63 08 00 78`. That vector is derived from the cited layout; it was not captured from the air.

Channel encryption is **AES-CTR with no MAC and no padding**, so ciphertext length equals plaintext length. A 16-byte key selects AES-128 and a 32-byte key selects AES-256. Decryption is the same operation as encryption ([CryptoEngine.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/CryptoEngine.cpp)). The 16-byte IV is the packet id written as a uint64 little-endian (bytes 0–7, upper half zero), then the sender's node number as a uint32 little-endian (bytes 8–11), then four zero bytes. The firmware sets a 4-byte counter, but a payload never exceeds 15 blocks, so the counter cannot wrap. Standard 128-bit big-endian CTR therefore produces identical output, which means ESP-IDF's hardware AES or mbedtls `aes_crypt_ctr` works unchanged. The default key is `d4 f1 bb 3a 20 29 07 59 f0 bc ff ab cf 4e 69 01` ([Channels.h](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Channels.h)). A new default channel stores a 1-byte PSK of `0x01` ("AQ=="). The expansion rule maps index N to the default key with its last byte increased by N−1. Index 0 means no encryption. Keys of 2–15 bytes are zero-padded to 16, and keys of 17–31 bytes are zero-padded to 32 ([Channels.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Channels.cpp)). Here is a self-computed check vector (OpenSSL, not taken from firmware, so validate it against a real capture). With the default key, from 0x12345678 and id 0xABCD, the IV is `cdab0000000000007856341200000000`, and the plaintext `08 01 12 02 68 69` (TEXT "hi") encrypts to `4d 75 77 d5 e0 02`.

The header's `channel` byte is a filter hint: the XOR of every byte of the channel name, XORed with the XOR of every byte of the expanded key. Default LongFast gives **0x08** ([Channels.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Channels.cpp)). Collisions are expected. The receiver therefore tries every channel whose hash matches, decrypts, and accepts the first result that decodes as a protobuf with `portnum != 0`. It treats `UNKNOWN_APP` as "bad psk?" ([Router.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Router.cpp)). The (from, id) pair is both the dedupe key and the CTR nonce, so it must never repeat. Meshtastic's `generatePacketId()` keeps a 10-bit rolling counter in the low bits and puts random bits above it ([Router.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Router.cpp)). Node numbers come from the last four MAC bytes (big-endian). Values 0–3 are reserved, and on a collision the node picks a random replacement. The user id string is `"!%08x"` ([NodeDB.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/NodeDB.cpp)).

Version 2.8 adds an opt-in AES-CCM "AEAD channel" (`ChannelSettings.use_aead`, field 8). It uses a 12-byte tag and AAD = from‖to, and XORs 0xAE into the channel hash ([CryptoEngine.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/CryptoEngine.cpp), [channel.proto](https://github.com/meshtastic/protobufs/blob/569a2b3ae7b6bda1a7ab177463a55d8ede3bef53/meshtastic/channel.proto)). The default LongFast channel does not use AEAD. Supporting it costs little and would put a new firmware ahead of anything that implements only CTR.

## Protobufs, flooding and PKI make a node a citizen, not a sniffer

Under the encryption sits a `meshtastic.Data` message with these fields: `portnum = 1`, `payload = 2` (bytes), `want_response = 3`, `dest = 4`, `source = 5`, `request_id = 6`, `reply_id = 7`, `emoji = 8`, `optional bitfield = 9`, and `xeddsa_signature = 10` (new in 2.8) ([mesh.proto](https://github.com/meshtastic/protobufs/blob/569a2b3ae7b6bda1a7ab177463a55d8ede3bef53/meshtastic/mesh.proto)). Fields 4–8 are `fixed32`, which is wire type 5 (4 bytes little-endian). The usual hand-encoding mistake is to write them as varints. Originators always set `bitfield`, with bit 0 = ok-to-MQTT and bit 1 = want_response ([Router.h](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Router.h)). The ports a messaging client needs are TEXT_MESSAGE_APP (1, raw UTF-8), POSITION_APP (3), NODEINFO_APP (4), ROUTING_APP (5), TELEMETRY_APP (67) and TRACEROUTE_APP (70). WAYPOINT (8), NEIGHBORINFO (71) and STORE_FORWARD (65) are worth adding later ([portnums.proto](https://github.com/meshtastic/protobufs/blob/569a2b3ae7b6bda1a7ab177463a55d8ede3bef53/meshtastic/portnums.proto)).

`User` carries id, long_name, short_name, `hw_model` and `role`, and **`public_key = 8`, which peers need before they can DM you**. A T-Deck Plus should report `hw_model = T_DECK (50)`, because the protobufs have no separate Plus value. `Position` uses `sfixed32 latitude_i/longitude_i` in degrees × 1e7, plus time, altitude, satellite count and `precision_bits = 23`. `Routing` is a oneof of route_request, route_reply and `error_reason` ([mesh.proto](https://github.com/meshtastic/protobufs/blob/569a2b3ae7b6bda1a7ab177463a55d8ede3bef53/meshtastic/mesh.proto)). The size rule is `encoded Data + 16 ≤ 255`, with 12 more bytes reserved for PKI or AEAD ([Router.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Router.cpp)). The protobuf constant `DATA_PAYLOAD_LEN = 233` bounds the inner payload. The commonly quoted "237" does not appear in the source. Telemetry's field layout lives in telemetry.proto and has not been extracted yet. The fastest and safest route is to generate nanopb code straight from the official `.proto` and `.options` files.

Relaying follows "managed flooding". A node that hears a packet not addressed to itself, with `hop_limit > 0`, `id != 0`, and `next_hop` either unset or equal to its own byte, queues a relay with `hop_limit − 1` and its own byte in `relay_node`. CLIENT_MUTE nodes, and nodes with rebroadcast mode NONE, do not relay ([NextHopRouter.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/NextHopRouter.cpp), [FloodingRouter.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/FloodingRouter.cpp)). The delay is what keeps the mesh quiet. The slot time is about 44 ms on LongFast. Original sends wait `random(0, 2^CW) × slot`, with CW scaled 3–8 by channel utilization. Non-router rebroadcasts wait `2·CWmax·slot + random(0, 2^CW) × slot`, with CW mapped from SNR between −20 and +10 dB. The result is that weaker-signal (more distant) receivers relay first ([RadioInterface.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/RadioInterface.cpp)). If the node hears the same (from, id) while waiting, it cancels its own relay. ROUTER and ROUTER_LATE are the exceptions. A duplicate with a higher hop_limit upgrades the queued copy. Reliability uses explicit ACKs. A `want_ack` unicast addressed to us is answered on ROUTING_APP with `Routing{error_reason = NONE}`, `request_id` = original id, sent back to the original sender on the same channel. The response's hop limit is hops used + 2, capped at the configured limit ([MeshModule.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/MeshModule.cpp)). A broadcaster counts overhearing its own packet being relayed as an implicit ACK. Senders retry 3 times ([ReliableRouter.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/ReliableRouter.cpp)).

PKI direct messages are where half-implementations break. The scheme is `shared = SHA256(X25519(my_priv, peer_pub))` with AES-256-CCM, an 8-byte tag, and a 13-byte nonce taken from the same id/from buffer. A random 32-bit `extraNonce` overwrites bytes 4–7 of that buffer. Note that this is bytes 4–7, not 12–15. The on-air payload is `ciphertext ‖ tag(8) ‖ extraNonce(4 LE)`, and the header's channel byte is 0 ([CryptoEngine.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/CryptoEngine.cpp), [aes-ccm.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/aes-ccm.cpp)). A sender uses PKI only when all of these hold: the packet is its own, it is not in ham (licensed) mode, it holds a 32-byte private key, the destination is a unicast whose key it knows, and the port is not TRACEROUTE, NODEINFO, ROUTING or POSITION. A receiver attempts PKI decryption only when `channel == 0`, the packet is addressed to it, and the payload exceeds 12 bytes ([Router.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Router.cpp)). From v2.7.26 onward, receivers log "Rejecting legacy DM" and drop any channel-encrypted TEXT message addressed to them ([v2.7.26 Router.cpp](https://github.com/meshtastic/firmware/blob/v2.7.26.54e0d8d/src/mesh/Router.cpp)). A firmware without PKI can therefore chat on the channel but cannot DM a current node.

Version 2.8 also signs broadcasts, NodeInfo and Position with 64-byte XEdDSA signatures, and adds `Routing.ack_proof` ([Router.cpp](https://github.com/meshtastic/firmware/blob/0d3da2dcda5d83fe8ecfb08ce23c9ef77464d39b/src/mesh/Router.cpp), [config.proto](https://github.com/meshtastic/protobufs/blob/569a2b3ae7b6bda1a7ab177463a55d8ede3bef53/meshtastic/config.proto)). The default receive policy, `checkXeddsaReceivePolicy`, has not been read. It is plausible that unsigned packets are still accepted under it, but that needs testing against a 2.8 node before anyone relies on it.

## GPIO10 first, then a shared SPI bus with three chip selects

LilyGO's pin file and Meshtastic's variant agree on every GPIO number ([LilyGO utilities.h](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/examples/UnitTest/utilities.h), [Meshtastic variant.h](https://github.com/meshtastic/firmware/blob/develop/variants/esp32s3/t-deck/variant.h)). The T-Deck and T-Deck Plus share one map. The only difference is that the Plus routes its internal GPS through the Grove pins, which leaves the Grove port unusable ([LilyGO README](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/README.MD)).

| Block | Pins (ESP32-S3) | Notes |
|---|---|---|
| Peripheral power | **10 → HIGH first** | Feeds keyboard C3, backlight, SD, trackball, amp, mic |
| Shared SPI | SCK 40, MOSI 41, MISO 38 | CS: LoRa 9, TFT 12, SD 39 (all OUTPUT HIGH before `SPI.begin`) |
| SX1262 | CS 9, RST 17, BUSY 13, DIO1 45 | DIO2 = RF switch, DIO3 = TCXO 1.8 V, OCP 140 mA |
| ST7789 | DC 11, CS 12, RST none, BL 42 | 240×320 native, rotation 1, INVON, RGB, 40 MHz write |
| I2C | SDA 18, SCL 8 | Keyboard 0x55, GT911 0x5D/0x14 (INT 16), ES7210 0x40 |
| Trackball | Up 3, Right 2, Down 15, Left 1, click 0 | Edge-counted pulses with INPUT_PULLUP; GPIO0 is also BOOT |
| Keyboard IRQ | 46 | Strapping pin; leave as input; both stacks poll instead |
| GPS UART | ESP RX 44, ESP TX 43 | Serial1; USB-CDC frees UART0 |
| Audio | Speaker I2S BCK 7 / WS 5 / DOUT 6; mic MCLK 48 / SCK 47 / LRCK 21 / DIN 14 | MAX98357A; ES7210 at 16 kHz |
| Battery | ADC 4 (ADC1_CH3) | 100k/100k divider: ×2 (LilyGO) or ×2.11 (Meshtastic) |

Order is the main trap. Meshtastic's `earlyInitVariant()` drives GPIO10 HIGH, sets CS 9/39/12 HIGH, and waits 100 ms. Its comments say SD detection fails otherwise, and that "if some boards are turned on late, ESP32 will reset due to low voltage" ([variant.cpp](https://github.com/meshtastic/firmware/blob/develop/variants/esp32s3/t-deck/variant.cpp)). LilyGO's UnitTest also sets MISO to INPUT_PULLUP before `SPI.begin(40, 38, 41)`. It re-asserts all three chip selects HIGH before every radio operation and guards TFT flushes with a FreeRTOS semaphore ([UnitTest.ino](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/examples/UnitTest/UnitTest.ino)). A new firmware should give the bus a single mutex shared by radio, display DMA and SD. Of the three, SD clock speed is the most divergent setting: LilyGO uses 800 kHz and Meshtastic uses 75 MHz ([variant.h](https://github.com/meshtastic/firmware/blob/develop/variants/esp32s3/t-deck/variant.h)). Start at a modest rate and raise it once SD reads are verified.

The radio settings are mostly fixed. Meshtastic declares `SX126X_DIO2_AS_RF_SWITCH` and `SX126X_DIO3_TCXO_VOLTAGE 1.8` ([variant.h](https://github.com/meshtastic/firmware/blob/develop/variants/esp32s3/t-deck/variant.h)). LilyGO calls a bare `radio.begin()`, which uses RadioLib's 1.6 V default, and then sets 22 dBm and a 140 mA current limit ([UnitTest.ino](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/examples/UnitTest/UnitTest.ino), [RadioLib SX1262.h](https://github.com/jgromes/RadioLib/blob/master/src/modules/SX126x/SX1262.h)). Use 1.8 V: it is the value proven on the large Meshtastic install base. The 915 MHz internal-antenna SKU is H737-A, and H737-03 is the external-antenna version ([LilyGO product page](https://lilygo.cc/products/t-deck-plus-meshtastic)). No source documents the internal antenna's gain or efficiency, so link-budget claims for that SKU are unproven.

The display is an ST7789 at 240×320, run in landscape with rotation 1. It has no reset pin, color inversion is ON, the order is RGB, and the format is RGB565. LilyGO's TFT_eSPI Setup210 deliberately leaves `TFT_BL` undefined, so your code must drive GPIO42 or the screen stays dark ([Setup210](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/lib/TFT_eSPI/User_Setups/Setup210_LilyGo_T_Deck.h)). The backlight driver is an AW9364 with 16 levels set by counting pulses. To use it, hold the pin LOW for 3 ms or more to turn it off, then drive it HIGH for 30 µs to reach level 16. Each LOW→HIGH pulse after that steps down one level ([UnitTest.ino](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/examples/UnitTest/UnitTest.ino)). Meshtastic's LovyanGFX config drives the same pin with 44.1 kHz PWM instead ([LGFX_T_DECK.h](https://github.com/meshtastic/device-ui/blob/master/include/graphics/LGFX/LGFX_T_DECK.h)), and both methods evidently work. The Plus panel differs from the original T-Deck's. LilyGO ships an alternate ST7789V init sequence ending in 0x21 (invert) and 0x29 (display on) for panels that look wrong. TFT_eSPI is broken on Arduino-ESP32 cores newer than 2.0.14 ([README](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/README.MD)). A new project on core 3.x or ESP-IDF should therefore use LovyanGFX or a native esp_lcd driver, as Meshtastic does.

The input devices each have quirks. The keyboard is an ESP32-C3 acting as an I2C slave at 0x55, clocked at 100 kHz. Reading one byte returns 0x00 when no key is pending and an ASCII character otherwise. Enter is 0x0D, Backspace is 0x08 and Alt+C is 0x0C. Alt+B toggles the keyboard backlight inside the C3 and sends nothing to the host. Write commands are `0x01 <duty>` (backlight), `0x02 <duty>` (Alt+B default, accepted only if >30), `0x03` (raw mode: 5 column bytes × 7 row bits) and `0x04` (back to key mode) ([Keyboard_ESP32C3.ino](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/examples/Keyboard_ESP32C3/Keyboard_ESP32C3.ino)). The source has a missing `break` that makes command 0x01 fall through into 0x02, so send exactly two bytes per write. The C3 also buffers only one character at a time, so poll every 10–20 ms or fast typing will drop keys.

Raw matrix mode is the route to proper modifier chords and key-repeat, and both stacks ignore it. It depends on the installed C3 firmware supporting it, so probe for it before relying on it.

The GT911 touch controller has no reset line, so you cannot force its address. Probe 0x5D first, then 0x14. For landscape, map it with max coordinates 320×240, swapXY on, and Y mirrored ([UnitTest.ino](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/examples/UnitTest/UnitTest.ino)). LilyGO's "TouchFix" image repairs dead touch on rounded-corner Plus screens. LilyGO warns that it breaks rectangular-screen units ([firmware README](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/firmware/README.MD)). Its log ("WriteConfig version char :0") suggests it rewrites the GT911 config block. That is an inference: LilyGO does not publish the source. Your firmware should never write GT911 config unprompted.

The GPS comes in two module variants, and LilyGO's own schematics show both. One is a u-blox MIA-M10Q (dated 24-03-29). The other is a Quectel L76K (dated 24-08-12), which suggests a mid-2024 production switch ([schematics](https://github.com/Xinyuan-LilyGO/T-Deck/tree/master/schematic)). No source says which one a given 915 MHz unit ships with, so detect it at runtime. To detect an L76K, open the port at 9600 baud, send `$PCAS03,…*02` and then `$PCAS06,0*1B`, and wait for a `$GPTXT,01,01,02` reply. If none arrives, try UBX CFG/RATE polls at 38400, 115200 and 9600 to find the M10 ([UnitTest.ino](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/examples/UnitTest/UnitTest.ino)). Neither pin map routes PPS to a GPIO.

Power management has hard limits. The charger is a TP4065B, and no source maps its CHRG pin to the ESP32, so charge state has to be inferred from the voltage trend. LilyGO's deep sleep fades the backlight, sleeps touch and the panel (SLPIN 0x10), lets GPIO10 drop, and wakes on GPIO0 through ext1. It draws **about 240 µA** in that state ([UnitTest.ino](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/examples/UnitTest/UnitTest.ino)). Waking on LoRa is a different case: GPIO10 must be held HIGH and the wake trigger must be DIO1 (GPIO45, active-high), and the sleep current then rises by an unmeasured amount.

On the build side, LilyGO's reference setup is PlatformIO `espressif32@6.3.0` (Arduino core 2.0.9) with 16 MB QIO flash at 80 MHz and **`memory_type qio_opi` for the 8 MB OPI PSRAM**. It uses `default_16MB.csv` with USB-CDC on boot ([boards/T-Deck.json](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/boards/T-Deck.json), [platformio.ini](https://github.com/Xinyuan-LilyGO/T-Deck/blob/master/platformio.ini)). Meshtastic's board file matches it and adds a 1200-bps-touch reset for its web flasher ([t-deck.json](https://github.com/meshtastic/firmware/blob/develop/boards/t-deck.json)). With CDC on boot, never block on `while(!Serial)`, or the device hangs on battery.

## Every incumbent leaves the same four gaps open

The field divides into Meshtastic firmware, MeshCore firmware, and everything else. Meshtastic's LVGL-based MUI (device-ui, GPL-3.0) is the official T-Deck UI. It has node lists, channels, chat with ACKs, and raster maps loaded from SD or WLAN ([device-ui](https://github.com/meshtastic/device-ui)). Its constraints are structural. The client API allows only one connection, so **a phone app cannot connect while MUI runs**, and some settings still require a phone ([MUI docs](https://meshtastic.org/docs/configuration/device-uis/meshtasticui/)). Navigation is touch-centric, and the BaseUI alt+c keyboard shortcuts are unavailable under MUI ([T-Deck docs](https://meshtastic.org/docs/hardware/devices/lilygo/tdeck/)).

Open bugs show the cost. Notifications fire even when disabled, and the device fails to wake after a few idle hours on 2.7.26 ([device-ui #339](https://github.com/meshtastic/device-ui/issues/339)). Long-pressing the Bluetooth icon crashes 2.8.1 ([device-ui #436](https://github.com/meshtastic/device-ui/issues/436)). The fallback BaseUI is sluggish on the Plus, with multi-second touch latency and a broken free-text keyboard ([firmware #11921](https://github.com/meshtastic/firmware/issues/11921)). Even so, users stay on it because WiFi and Bluetooth work fully only there ([firmware #9018](https://github.com/meshtastic/firmware/issues/9018)).

On the MeshCore side, MeshCore Ultra is the polished standalone option, built by the MeshCore creator. It is closed source, gates some features behind a paid unlock key, and speaks MeshCore rather than Meshtastic ([MeshCore FAQ](https://docs.meshcore.io/faq/?h=)). Community MeshCore forks such as WADAMESH (Plus) and Meck (Pro/Max) inherit that incompatibility ([Meck wiki](https://github.com/pelgraine/Meck/wiki)). The rest of the field has no Meshtastic mesh support at all: Bruce (pentest), bmorcelli's Launcher, Tactility (OS), acid-drop (IRC) and Blackout Comms ([Bruce](https://github.com/BruceDevices/firmware), [Launcher](https://github.com/bmorcelli/Launcher), [acid-drop](https://github.com/acidvegas/acid-drop), [Blackout Comms](https://www.offgridcomms.club/firmware/esp32/tdeck_firmware.html)).

Owner complaints converge on battery and input. One reviewer gets about 12 hours of medium use from the 2000 mAh cell and says LilyGO admits the device only estimates charge ([The Secure Dad](https://www.thesecuredad.com/post/lilygo-t-deck-plus-review-standalone-meshtastic-without-your-phone)). Users single out the backlight as the drain ([Discussion #308](https://github.com/orgs/meshtastic/discussions/308), anecdotal). No source supplies measured current figures, so battery-life targets remain to be established on the bench.

| Gap | Incumbent behavior | What a new firmware should do |
|---|---|---|
| Keyboard-first UX | MUI touch-centric; BaseUI keyboard broken in free text | Full keyboard + trackball navigation, hotkeys, raw-matrix modifiers |
| Phone coexistence | MUI blocks the phone client | Serve the Meshtastic BLE client API alongside the on-device UI |
| Power and battery | Backlight-heavy, voltage-only estimate, wake bugs | Aggressive backlight/keyboard-light timeouts, LoRa-IRQ light sleep, calibrated voltage curve with ×2.11 correction |
| Stability | Open crash/wake/notification bugs | Single SPI-bus mutex, deterministic init order, watchdog-clean tasks |
| Maps | MUI raster tiles | Read MUI's `/maps/<style>/{z}/{x}/{y}.png` layout so existing packs work |
| Distribution | Launcher dual-boot common | Ship merged 0x0 image plus app-only bin for Launcher/OTA |

The map choice is the easiest win. MUI reads 256×256 PNG slippy tiles (8-bit palette recommended) from `/map/` or `/maps/<style>/z/x/y` on FAT32 or exFAT SD cards. Prebuilt packs run to about 1.4 GB for the USA at zoom 1–12 ([MUI docs](https://meshtastic.org/docs/configuration/device-uis/meshtasticui/), [device-ui/maps](https://github.com/meshtastic/device-ui/tree/master/maps)). Matching that layout makes every existing pack drop-in compatible. If the firmware downloads tiles over WiFi, it must respect provider terms. Thunderforest and Geoapify require API keys, and OSM forbids bulk downloads.

Distribution should follow the same principle. Merged images flash at 0x0. Writing one at 0x10000 breaks the partition layout ([PlatformIO forum](https://community.platformio.org/t/how-to-use-esptool-exe-to-upload-application-firmware-bin-and-spiffs-bin/54003)). Shipping a standard app partition alongside the merged image lets users dual-boot with Bruce or MUI through Launcher, which lowers the cost of trying a new firmware.

Licensing shapes the build. Meshtastic's device-ui is GPL-3.0, so copying its code makes the new firmware GPL. An implementation written from the protocol spec above avoids that only if no GPL source is copied. The licenses of the firmware, protobufs, LVGL and RadioLib repos have not been confirmed against their own license files.

## Conclusion

The protocol is smaller than its reputation, but what decides interoperability has moved. Getting a T-Deck to *hear* LongFast takes about a day: the seven radio parameters, the header, CTR and the XOR hash are all deterministic, and the check vectors above make them testable offline. What now separates a real Meshtastic node from a receiver is the 2.7+ requirement for PKI direct messages and the incoming 2.8 layer of XEdDSA signatures, ack_proof and AEAD channels. A from-scratch firmware should treat X25519/CCM as part of the minimum viable product, and should verify 2.8's unsigned-packet policy against a live node before release. The biggest risk is not the radio. It is that the protocol keeps changing in point releases, so the project needs a regression harness that tests against each Meshtastic release line (2.5, 2.7, 2.8).

On the product side, the winning angle is restraint, not features. Every incumbent fails on the basics of this specific device: the keyboard, the phone link, the backlight and a wake that works. A firmware that powers up in the right order, shares the SPI bus correctly, uses raw keyboard mode, keeps the BLE client API available, reads MUI's map packs and publishes measured battery life would be the first T-Deck Plus firmware that is both Meshtastic-native and designed around the hardware. Three things remain unknown and should be bench-measured before making promises. They are the internal antenna's real performance, the GPS variant on current 915 MHz stock, and actual current draw in each power state.
